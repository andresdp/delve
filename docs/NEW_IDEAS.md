* The taxonomy generation process should allow to start from an existing taxonomy, and run the whole Langgraph graph starting from that basis. Optionally, there can be some user feedback to take into account in the process.

* The taxonomy process can be run in 2 modes: i) train, which is the current mode in which the taxonomy is progressively built and updated; and ii) test, in which the existing taxonomy is not modified, but new batches of documents can be added to the existing dimensions. 

* Since the taxonomy generation process indirectly produced a grounded theory (through open coding, selective coding, etc), it should be able to generate a markdown respresentation of this theory, including a mermaid chart showing the main concepts and relationships of the theory. 

* It should be aable to run the same generation process multiple times (for the same inputs) so as to assess the consistency and robustness of the generated taxonomy.

* Currently, when generating and reviewing a current snapshot of the taxonomy, the prompts specify several quality criteria to be considered/checked by the LLM. These criteria should be implemented as separate llm-as-a-judge metrics, for instance, using GEval from the Deepeval library, to get a scoreboard. Furthermore, once a taxonomy is available, it should be possible to execute these criteria in a standalone mode to get a scoreboard. https://deepeval.com/docs/metrics-llm-evals

* Check the differences (and potential similarities) between the saturation and review nodes. Would it be possible to have a feedback loop (return arc) in the review node?

* An alternative strategy for checking the taxonomy, once the dimensions and values are provided, is to sample points (i.e., solutions) in the space that combine more than one value across the dimensions. These alternative solutions could be checked for consistency, diversity or other properties.

* Multi-persona grounded theory: today every LLM-calling node in the graph (`open_code_minibatch`, `generate_taxonomy`, `update_taxonomy`, `review_taxonomy`, `check_saturation`, the borderline adjudication inside `value_consolidator.py`) is a single fixed system prompt and a single model — one analyst's voice applied uniformly to the whole corpus. Real grounded theory gets some of its validity from multiple coders/lenses catching what one misses (theoretical sensitivity/triangulation), so it's worth extending the pipeline to optionally run with several distinct "personas" (e.g. security/compliance, performance/scalability, maintainability, product/UX — whatever lenses suit the `use_case`) instead of one. Two escalating places to do this, in planned build order:

  - **A. Multi-persona open coding.** Add a `personas:` list to `config.yaml` (id, a short lens description, optional per-persona model override) and give `open_coding.md` a `{persona}` slot (empty string by default so a config with no personas behaves exactly as today — non-breaking). `_setup_open_coding_chain` in `open_coder.py` builds one chain per persona instead of one chain total; `open_code_minibatch` fans those chains out per document (the function already does `asyncio.gather` with a semaphore over documents, so this is "loop over personas × documents" inside the same node, no `graph.py` changes needed). Add an optional `persona` field to `OpenCode` in `schemas.py` so each code stays attributable. Impact: cost multiplies by N at the open-coding stage specifically — the cheapest of the two escalations per-call, but it runs every minibatch, and each document can now yield up to 8 codes × N personas, so code volume feeding axial coding grows fast. Different personas will often name the same underlying decision differently, so `value_merge_distance_threshold`/`value_merge_borderline_band` consolidation (already in `value_consolidator.py`) goes from a cleanup detail to load-bearing — it's the mechanism that keeps N-persona open coding from just handing axial coding N synonymous copies of the same concept. Payoff only materializes if the personas are genuinely distinct analytical concerns grounded in the `use_case`, not cosmetic role-play — that's the real risk with this option, not the extra LLM spend.

  - **B. Multi-persona axial coding** (`generate_taxonomy` / `update_taxonomy`). Same persona list, but now each persona gets its own full axial-coding chain over the *same* open codes, producing its own candidate `List[Cluster]` per iteration — real triangulation, since each persona independently organizes the evidence into dimensions rather than just tagging concepts. This is the more invasive change: every downstream node (`check_saturation`, `review_taxonomy`, `consolidate_values`, `select_dimensions`) assumes exactly one "current" taxonomy via `state.clusters[-1]`, and `clusters` is `Annotated[List[List[Dict]], operator.add]` — an accumulator across the *whole run*, one entry per iteration. If N persona branches each returned straight into `clusters`, the "latest is `clusters[-1]`" invariant every later node relies on would break (N entries per iteration instead of one, and "latest" would depend on branch-completion order, not persona identity). So persona drafts need to land in a separate, per-iteration-only state field first; a new reconciliation node then merges them into a single `List[Cluster]` and only *that* gets appended to `clusters`. The reconciliation logic doesn't need to be invented from scratch: `evaluation/consistency.py`'s `compare_taxonomies` already does N-way dimension alignment (embed name+description+values, greedily merge below `evaluation_consistency_threshold`, judge-adjudicate the borderline band) — it currently only *reports* agreement between saved taxonomies (and isn't wired into the CLI yet), but the same alignment pass, extended to actually synthesize a merged dimension list from the recurring groups (plus a judged keep/drop call on the one-offs) instead of just reporting them, is most of what the new merge node needs. Inserting that merge node immediately after the persona fan-out and *before* `check_saturation` is the key design choice: everything downstream keeps reading `state.clusters[-1]` exactly as it does today, so `check_saturation`, `review_taxonomy`, `consolidate_values`, and `select_dimensions` need no changes at all, and saturation is simply evaluated on the one reconciled taxonomy rather than needing a per-persona definition. Fan-out itself is best done with LangGraph's `Send` API rather than a manual loop, so each persona's axial-coding call is its own traceable node run. Impact: cost multiplies by N using `configuration.model` (the more expensive of the two models) at *every* axial-coding iteration — both the one-time `generate_taxonomy` call and every subsequent `update_taxonomy` call — plus one merge pass (an embedding batch and occasional judge calls) per iteration; for a corpus with many minibatches this is a materially larger recurring cost than option A. Persona-branch merge order should be sorted deterministically (e.g. by persona id) before reconciliation, since async fan-out otherwise makes result ordering — and therefore which draft "wins" a near-tie — nondeterministic. Worth adding an optional `sources: List[str]` (contributing persona ids) to `Cluster`/`Value` for provenance, surfaced later in `report_renderer.py`, but that's a phase-two nicety, not required to make the merge work.
