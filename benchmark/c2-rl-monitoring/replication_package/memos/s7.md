## Memo 7: Automated Rollback Architecture for Production Models (Source 7)

**URL**: https://apxml.com/courses/monitoring-managing-ml-models-production/chapter-4-automated-retraining-updates/automated-rollback

**Open Codes & Quotes**:
- RollbackSafetyNet: "Automated rollback mechanisms are an essential component of a mature MLOps strategy, providing a safety net to quickly revert to a previously known stable state when things go wrong"
- TriggerTaxonomy: "Common triggers include: performance metric thresholds, error rate spikes, latency violations, drift detection alarms, resource consumption anomalies, business KPI impact, manual trigger"
- ThresholdTuning: "Setting thresholds too aggressively can lead to 'flapping,' where the system constantly rolls back and forth. Setting them too loosely defeats the purpose"
- BlueGreenRollback: "rapidly shifting 100% of the traffic back to the previous stable version — managed at the load balancer, service mesh, or API gateway level"
- VersionPointerUpdate: "updating this pointer — the deployment system interacts with the model registry to retag the previous stable version as current production"
- RLStatefulComplexity: "If your model involves state (e.g., certain online learning or reinforcement learning scenarios), the rollback process might need to handle state restoration or reset, adding complexity"
- TestTheRollback: "the automated rollback mechanism itself must be tested regularly — simulate failure conditions and verify that the rollback triggers correctly"
- AuditTrail: "Every automated rollback event must be logged comprehensively, detailing the trigger condition, the timestamp, the version rolled back from, and the version rolled back to"

**Axial Relations**:
Causal (new model deployment introduces unexpected degradation, latency, or drift) → Phenomenon (production model behaving worse than previous version) → Context (live production ML/RL system with continuous deployment pipeline) → Strategy (automated rollback via traffic shifting, version pointer update, or configuration change, triggered by performance/drift/error monitors) → Consequence (rapid recovery to known-good state, or prolonged exposure to degraded model if rollback is too slow or missing)

**Dimensions**:
- RollbackSpeed: immediate traffic shift (blue/green) vs version pointer update (seconds to minutes) vs configuration redeploy (minutes)
- TriggerSensitivity: aggressive thresholds (fast response, risk of flapping) vs conservative thresholds (slower response, less noise)
- StateComplexity: stateless models (simple rollback) vs stateful RL agents (need state restoration/reset)
- RollbackScope: full traffic revert vs partial (canary only) vs gradual wind-down

**Forces/Drivers**:
- "RollbackLatency": time between detecting a problem and completing the rollback determines the blast radius of a bad deployment
- "FlappingRisk": overly sensitive triggers cause constant rollback/redeploy cycles, creating instability worse than the original problem
- "StatefulRollbackComplexity": (RL-specific) RL agents carry learned state that must be handled during rollback — cannot simply swap model artifacts like stateless prediction models
- "AuditRequirement": regulatory and operational need for comprehensive logging of every rollback event

**Cross-links**:
- **ADD 3 (Automated Response Mechanism)**: This source provides deep implementation detail for the "policy rollback" option. The execution strategies (blue/green traffic shift, version pointer, configuration change) are sub-options within rollback. The RL-specific insight about stateful rollback adds an important nuance: for RL agents, rollback is architecturally more complex than for stateless models because learned policy state, replay buffers, and internal agent state must be handled.
- **ADD 2 (Production Monitoring Signal Selection)**: The trigger taxonomy (performance thresholds, drift alarms, error spikes, business KPIs, latency) confirms that multiple signal types feed into rollback decisions, consistent with ADD 2's multi-signal monitoring approach.
- **ADD 5 (False Alarm Rate Control)**: The "flapping" problem — rollback triggered too frequently by noisy signals — is the operational consequence of poor false alarm control, directly connecting to S2's BFAR work.
- **S3 cross-link**: S3's self-healing agent used checkpoint rollback with learning rate reduction. This source formalises the rollback execution strategies that S3 implemented informally, and adds the important point that rollback mechanisms must be *tested* regularly ("simulate failure conditions").
