**Open Codes & Quotes**:
- CaseBasedTesting: "Having a ground-truth for some trivial searches + products and checking if the model does those right (in non-exploratory mode)"
- ABPolicyTesting: "Letting the agent learn in batch-mode and doing A/B tests for the current model / new model"
- MeanRewardThreshold: "Measuring mean reward and setting a threshold. If the mean reward of the agent drops below the threshold, reset the agent to a past 'save' state"
- OODDataMonitoring: "monitor the data, then retrain the agent if new data is statistically out-of-sample"
- TechnicalDebt: reference to Google's "Machine Learning: The High Interest Credit Card of Technical Debt" — systems degrade over time
- GracefulExit: "follow fundamental production engineering techniques (e.g., test coverage and graceful exit)"

**Axial Relations**:
Causal (changing products, search terms, language in production) → Phenomenon (RL agent learns something weird / needs to be stopped) → Context (RL recommendation agent in e-commerce search) → Strategy (four approaches: case-based ground truth, batch A/B testing, mean reward thresholding with rollback, OOD data monitoring) → Consequence (timely detection and rollback or undetected degradation)

- MonitoringApproach: reward-based (threshold) vs data-based (OOD) vs behavioural (case-based)

### Notes

The questioner's four approaches represent a practitioner's intuitive decomposition of the monitoring problem that maps cleanly onto our ADD structure. Notably, the questioner proposes the "naive simple mean" approach for reward monitoring — exactly the method that s2 (Greenberg & Mannor) proved is sub-optimal compared to the covariance-weighted test. This validates our theory's practical relevance: practitioners default to naive approaches, and the theory identifies better alternatives.

The reference to Google's ML technical debt paper reinforces the "systems degrade over time" framing that underpins the entire monitoring pipeline.
