## Memo 9: RLHF Alignment Drift Monitoring (Source 9)

**URL**: https://apxml.com/courses/rlhf-reinforcement-learning-human-feedback/chapter-7-rlhf-evaluation-deployment/deployment-considerations-rlhf

**Open Codes & Quotes**:
- AlignmentDriftConcept: "Alignment is not a one-time achievement; it's a state that needs continuous monitoring and maintenance. Models can drift, user expectations can change, and new vulnerabilities might emerge once the model interacts with diverse inputs"
- RewardModelScoring: "Periodically sample production traffic (prompts and responses) and score the responses using the frozen reward model from the RLHF training phase. A significant decrease in average reward scores over time could indicate performance degradation or drift"
- RewardModelValidityCaveat: "Be cautious, as this relies on the assumption that the reward model remains a valid proxy for human preference"
- KLDivergenceMonitoring: "track the KL divergence between the deployed policy and the original SFT policy on production samples. A large, sustained increase might suggest the model has drifted significantly, potentially into undesirable behavior regions"
- SafetyFlags: "Implement classifiers or keyword detectors to flag potentially harmful, biased, or inappropriate outputs. Monitor the rate of such flags"
- HelpfulnessProxies: "response length, user engagement signals (e.g., thumbs up/down), or task completion rates"
- HITLMonitoring: "Automated metrics provide scale, but human review remains important for catching subtle issues. Establish a process for periodic human review of sampled production interactions"
- RetrainingTrigger: "When monitoring indicates performance degradation or when substantial amounts of new preference data become available, retraining is necessary"
- UpdatedRewardModel: "Retraining might involve: Gathering New Data, Updating the Reward Model with augmented preference dataset, Resuming PPO, Thorough Evaluation"
- OnlineRLAdaptation: "research looks at methods for online adaptation where the model learns continuously from live user feedback. This requires strong safety mechanisms to prevent rapid negative adaptation"
- RollbackStrategy: "Have a clear and tested plan to quickly roll back to a previously known stable version if the deployed model exhibits severe, unexpected issues"
- ABTesting: "Implement infrastructure that allows for A/B testing or canary releases — deploying a new RLHF model candidate to a small fraction of users"

**Axial Relations**:
Causal (diverse production inputs + evolving user expectations + emerging vulnerabilities post-deployment) → Phenomenon (alignment drift — RLHF-aligned model gradually loses alignment with human preferences in production) → Context (deployed RLHF-trained language models interacting with real users) → Strategy (continuous monitoring via reward model scoring + KL divergence tracking + safety flags + human review; response via retraining with updated reward model or rollback) → Consequence (maintained alignment and safety, or gradual alignment erosion undetected until user harm occurs)

**Dimensions**:
- AlignmentMonitoringSignal: reward model scores (proxy, may drift) vs KL divergence from reference (structural) vs safety flag rate (output-level) vs human review (ground truth, expensive)
- RewardModelTrust: frozen RM as reliable proxy vs RM itself becoming stale (reward model validity caveat)
- RetrainingScope: update reward model + resume PPO (comprehensive) vs fine-tune policy only (cheaper) vs online adaptation (continuous but risky)

**Forces/Drivers**:
- "AlignmentImpermanence": alignment achieved through RLHF is not permanent — production interactions, changing user expectations, and emerging vulnerabilities cause drift
- "RewardModelStaleness": the frozen reward model used for monitoring may itself become an invalid proxy over time as user preferences evolve — a meta-monitoring problem
- "SafetyFlagNoise": automated safety classifiers produce false positives; the flag *rate* must be tracked over time, not individual flags
- "HumanReviewCost": human evaluation is the gold standard for alignment but doesn't scale — must be sampled periodically

**Cross-links**:
- **ADD 2 (Production Monitoring Signal Selection)**: This source adds two RLHF-specific monitoring signals: (1) reward model scores on sampled production traffic — a proxy for alignment quality that S2's reward degradation test (ADD 4) doesn't cover because S2 monitors *actual environment rewards*, while this monitors *reward model predictions* on outputs; (2) KL divergence between deployed policy and reference SFT policy — a structural measure of how far the policy has drifted from its known-good baseline, distinct from S1's "policy entropy" metric.
- **ADD 4 (Reward Degradation Test Statistic)**: The reward model scoring approach is complementary to S2's environment-reward monitoring. S2 detects degradation in actual reward signals; this source detects degradation in the reward model's *assessment* of outputs. The two can diverge if the reward model itself becomes stale (the validity caveat).
- **ADD 6 (Reward Hacking Detection)**: The reward model validity caveat directly connects to S6's insight — if the agent is hacking the reward model, reward model scores will remain high while true alignment degrades. This source acknowledges this risk but doesn't propose a solution beyond the caveat.
- **ADD 3 (Automated Response Mechanism)**: Confirms rollback and A/B testing as response mechanisms, consistent with S1 and S7.
- **ADD 7 (Reward Hacking Mitigation)**: The retraining strategy (update reward model with new preference data, then resume PPO) is a maintenance approach that could serve as a mitigation for reward model staleness — refreshing the alignment signal periodically.
