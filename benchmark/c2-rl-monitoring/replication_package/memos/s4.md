## Memo 4: Offline RL Deployment Monitoring Patterns (Source 4)

**URL**: https://aiopsschool.com/blog/offline-reinforcement-learning/

**Open Codes & Quotes**:
- CovariateShift: "distribution shift: dataset lacks edge cases; policy takes unsafe action in production" — the static gap between offline training data and live environment
- DriftIndex: "Drift index: Statistical distance between dataset and live — KL or MMD on features" — feature-level distribution monitoring
- RewardProxyGap: "Reward proxy gap: Difference between offline reward and live proxy — Compare offline estimate vs live proxy" — monitoring divergence between offline evaluation and production performance
- SafetyViolationCount: "Safety violation count: Count of actions breaching safety rules — Zero tolerated breaches"
- ShadowDeployment: "Deploy policies as observers to compare offline predictions with real outcomes before acting"
- CanaryRollback: "Canary/blue-green rollout to production with monitoring and automated rollback"
- DriftUnnoticed: "Drift unnoticed: Gradual performance decline — Nonstationary environment — Continuous monitoring and retrain"
- EvaluationMismatch: "Good offline eval bad production — Poor offline evaluation method — Use multiple eval methods"
- RewardHackingProduction: "Reward hacking: High offline reward low live reward — Mis-specified reward — Redefine reward and add constraints"
- ObservabilityFocus: "Observability focuses on drift, policy performance, and safety SLOs"
- ConservativeObjective: "conservative objectives to avoid unsafe generalization" — safety mechanism for offline-RL policies entering production
- IncidentRunbook: "incidents include policy regressions, dataset corruption, or drift-related failures" — production incident categories for RL

**Axial Relations**:
Causal (covariate shift between offline training dataset and production environment + environment non-stationarity post-deployment) → Phenomenon (offline-RL-trained policy underperforms or behaves unsafely in production despite good offline evaluation) → Context (safety-critical or cost-sensitive production deployments where online exploration was avoided by design) → Strategy (shadow deployment for pre-production validation, feature-level drift monitoring via KL/MMD, reward proxy gap tracking, canary rollback, safety violation counting) → Consequence (safe deployment with gradual confidence building, or undetected drift and evaluation mismatch leading to production incidents)

**Dimensions**:
- ShiftType: static covariate shift (training data ≠ production from day one) vs dynamic drift (production environment changes over time) — offline RL faces both
- MonitoringLevel: feature distribution (KL/MMD) vs reward proxy vs safety violations vs action failure rate
- DeploymentGating: shadow deployment (observe only) vs canary rollout (limited traffic) vs full deployment
- EvaluationStrategy: single offline metric (risky) vs multiple evaluation methods (recommended) — "Use multiple eval methods"

**Forces/Drivers**:
- "CovariateShift": (new nuance on S1's DistributionShift) offline RL training data may systematically differ from production — this is a *structural* gap, not just environment change
- "EvaluationMismatch": offline evaluation metrics may correlate poorly with live performance — monitoring must bridge this gap
- "SafetyConstraints": (confirms S1) zero tolerance for safety violations drives conservative deployment patterns
- "EnvironmentNonStationarity": (confirms S1) gradual drift post-deployment can go unnoticed without continuous monitoring
- "RewardProxyWeakness": reward proxies used in production may diverge from true objectives — requires ongoing validation

**Cross-links**:
- **ADD 2 (Production Monitoring Signal Selection)**: This source adds feature-level drift monitoring (KL/MMD on input distributions) and reward proxy gap tracking as specific signals to monitor. These enrich the "RL-specific metric tracking" and "business outcome correlation" options with offline-RL-specific implementations. The drift index metric is distinct from S2's reward-signal-focused approach — it monitors *input distribution* rather than *output performance*.
- **ADD 3 (Automated Response Mechanism)**: This source confirms canary rollback and adds shadow deployment as a pre-production validation step. Shadow deployment sits between monitoring and response — it's a way to evaluate the policy in production without committing to it.
- **ADD 4 (Reward Degradation Test Statistic)**: The "evaluation mismatch" failure mode confirms S2's insight that naive metrics are insufficient. The source recommends using multiple evaluation methods to triangulate, paralleling S2's argument for covariance-weighted tests over naive means.
- **ADD 5 (False Alarm Rate Control)**: The source's alerting guidance ("Use thresholds tuned to historical variance to avoid false positives") confirms the need for controlled false alarm rates, though it doesn't propose a specific method like S2's BFAR.
- The **covariate shift** concept adds a new dimension to the DistributionShift driver from S1: in offline RL, distribution shift can be *inherent from the start* (training data never matched production), not just a consequence of environment change over time. This is a distinct monitoring challenge because it means the first deployment is already at risk, unlike online-trained agents which at least started in the correct distribution.
