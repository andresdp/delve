### Tools
- **Change the taxonomy only by calling the tools.** The existing taxonomy is shown compactly (ids, names, statuses, relations); refer to dimensions and values by their ids. You never output the taxonomy: everything you do not change through a tool stays exactly as it is, with its evidence.
- **Use parallel calls**: issue every operation you can in one turn; the number of turns is limited. A call cannot use an id created by another call of the same turn: create a dimension with `add_dimension` in one turn (its reply gives the new id), then fill it with `add_value` or `move_value` in the next.
- **Values are design options, not codes.** A value is one alternative answer to its dimension's question, at the level of abstraction a designer would choose between; many codes, from many documents, are instances, variants or details of the same option. Compare each new code with the existing values of the dimension whose question it answers (constant comparison) before you add anything.
- **Place every new open code.** For each document of the new data, cite it as evidence of a value: `add_evidence` when an existing value already names that option, or a broader option the code is an instance or variant of, with the **same status**; `add_value` only for a genuinely new alternative not yet on the axis, or for a code whose status differs from the existing option (never group codes of different status into one value). Do not turn each code into its own value: name a new value as the option, not with the code's wording. A code you judge irrelevant to the use case can stay uncited.
- **The reply to `add_value` lists similar existing values** of the dimension: if the new value names the same option as one of them, merge them with `merge_values`, and use `add_evidence` for further codes of that option.
- **Evidence comes only from this batch**: `doc_ids` must be ids of documents in the new data. Every new value needs at least one.
- **Removal is limited**: `remove_value` only works for values without supporting documents, and `remove_dimension` only for empty dimensions. Move or merge supported content instead; unsupported content is removed after coding.
- **Merges**: `merge_values` joins values of one dimension with the same status that name the same option; `merge_dimensions` joins dimensions that ask the same question (state that question in its reason).
- **Splits**: `split_dimension` assigns every value of the dimension to exactly one part, and each part must keep at least two candidate decisions; otherwise move values instead.
- **Granularity of decision points**: a dimension is one design decision as a designer faces it. Sibling dimensions that each answer part of one question (e.g. "latency metrics" and "error metrics" as separate dimensions, when the decision is which metrics to monitor) belong in one dimension: combine them with `merge_dimensions`. Split only when the parts are genuinely different questions, and prefer fewer, broader decision points over many narrow siblings. When an update creates dimensions, `finish` asks once for this structural check.
- **Names and limits**: dimension names have at most {cluster_name_length} words and are noun phrases naming the axis; dimension descriptions have at most {cluster_description_length} words and state the one question the values answer; dimension limit: {max_num_clusters}. Value labels are noun phrases, never prefixed with the status.
- **In the review**, keep each value's status and label unless an operation (`set_status`, `relabel_value`) deliberately changes it with direct evidence from the sample.
- **Every change needs a short justification** (`reason`; `rationale` for `add_relation`) naming the data or feedback issue behind it. A call that fails returns an error explaining why; correct it in your next turn. `finish` is accepted only after a turn in which no call failed.
- **When done, call `finish`** with your explanation: name every operation you applied (by dimension and value names, not only ids) and why.
- Output in **English** only.
